Search for "memory MCP server" and you get lists of nine or ten servers, and tutorials that end when one assistant on one laptop remembers your name in the next chat. That is a fair test for a personal assistant. A team has a different problem. Three agents work in three tools on two machines. A person changes the retry limit on Tuesday. On Thursday an agent in another tool has to get the new value, know who decided it, and not write the old one back.

Almost any server on those lists will store a sentence and return it. They differ in what happens with the second agent, the second machine and the second value, and that is the part a team has to check. This guide gives seven questions to ask, what five options document about each, and a test you can run in an afternoon.

Everything said here about other products was read in their own documentation on November 27, 2026. We describe what each one documents and quote no benchmark. These pages change often, so open the links before you rely on a detail.

## The seven questions

1. **Where does the memory live, and can a second machine reach it?** A file on a laptop, a database you run, or someone's cloud.
2. **Who can read what, and who enforces it?** A filter the caller passes is not the same thing as a permission the server checks.
3. **What happens when a value changes?** Either the old value is replaced, or it stays next to the new one, or it is kept as history and marked as old.
4. **Does an answer come back with its date and its source?** Without them the next agent cannot tell a decision from a guess.
5. **Who can overwrite or delete what a person decided?** Look at the delete tools in the list, then at what the credential you give an agent is allowed to call.
6. **Who writes the memory, and what leaves the machine to do it?** The agent may write records itself, or a model may extract them from the conversation. If a model does it, find out whose key it runs on and what text it is sent.
7. **What do you take with you when you leave?** An export you can run yourself, in a format you can read.

Four details in those pages decide most of the choice.

**A file on one machine is a memory for one machine.** The reference server describes itself as a basic implementation of persistent memory on a local knowledge graph. Each client starts its own server process and the file is on that machine's disk. By default it is `memory.jsonl` in the server's own directory, so set `MEMORY_FILE_PATH` to an absolute path that you back up. The README also says a file on a network filesystem is not safe, which rules out a shared drive as the way to give a second machine the same memory.

**A namespace is not a permission.** Graphiti's documentation says so in plain words: the application has to authorize each `group_id` before it passes it. For any product that scopes memory by an ID in the call, ask what stops agent B from passing agent A's ID. Where the server does enforce access, ask a second question: can the agent tell "nothing found" from "not allowed"? SurrealDB documents that a scoped read without a matching grant returns empty and is not refused. ValorBrain's `acl_me` returns the domains the caller can read and a count of documents hidden from it, so an empty answer can be told apart from a missing permission.

**"Remembers" and "knows which value is current" are two features.** Mem0's add page says new memories are added without overwriting or deleting existing ones. The reference server stores observations as strings with no date field. In both, a changed value leaves two statements in the store unless an agent finds the old one and updates or deletes it. Graphiti, SurrealDB Agent Memory and ValorBrain each document a time model in which the old value stays as history and a read can ask for a past date.

**Every tool list has delete tools.** The reference server lists `delete_entities`, `delete_observations` and `delete_relations`. Mem0 MCP lists `update_memory`, `delete_memory` and `delete_all_memories`. Graphiti lists `delete_entity_edge`, `delete_episode` and `clear_graph`. Find out which of them the credential you hand to an agent can call. SurrealDB ranks by the kind of source: a fact written as triples starts above a document, a document above a conversation turn, and every turn has the same trust whoever spoke. ValorBrain ranks by who is speaking: `human` > `designated` > `import` > `agent`. A weaker write over a value held by a stronger one becomes a proposal that waits for a person, and a token with no user behind it is capped at `agent`.

Two of the seven questions are not in the table. For question 6, Mem0's add runs an LLM extraction by default, Graphiti builds its graph with the LLM and embedding keys you supply, and with the reference server the agent writes entities and observations itself. For question 7, the reference server's memory is a file you already hold, and Graphiti's is a database you run. We did not read an export page for Mem0 or for SurrealDB Agent Memory, so ask them.

## Which one fits

- **One developer on one machine, who wants to open the memory in a text editor:** the reference server. It is the simplest thing that works, and the file is yours.
- **Hosted memory scoped per user, agent or app, with nothing to run:** Mem0 MCP.
- **A team that wants to own the graph and is ready to run a graph database and pay for the model calls:** Graphiti. Read the "experimental" note on the MCP server first.
- **A team already on SurrealDB, or one that wants every fact tied to a quote in its source:** SurrealDB Agent Memory.
- **A team where people decide, several agents in different tools must not contradict or overwrite them, and work passes from one agent to the next:** this is what ValorBrain is built for.

ValorBrain is the wrong pick if you need to run the engine yourself outside an Enterprise contract, or if you need to read the source. There is no community edition and the code is not public.

## The afternoon test

Run it on any candidate. You need two agents in two different tools, for example Claude Code and Codex, signed in as two different users if the product has users. A second machine is better than a second terminal.

1. **From agent A, record a decision.** "The webhook retry limit is 5. The owner decided it on November 10."
2. **From agent B, in a fresh session, ask for it.** "What is the webhook retry limit, who decided it, and when?" It passes if the value comes back with the date and the source and nobody pasted anything.
3. **From agent A, change it.** "The owner changed the retry limit to 3 on November 20." Ask again from B. It passes if 3 comes back alone, or 3 comes back marked current and 5 marked old. It fails if both come back as equals.
4. **From agent B, ask about the past.** "What was the retry limit on November 15?" It passes if the answer is 5.
5. **From agent B, try to overwrite it.** Have the agent write 10 with no person involved. There are three possible outcomes: the write replaces the value, it is refused, or it is queued for a person. Know which one you got before an agent does this by accident.
6. **From agent A, write something only A's user should see.** Ask for it from B. It passes if B does not get it. Note whether B can tell that something was withheld.
7. **Turn machine A off.** Ask B again. Then run the export and open the file.

Read the result this way:

- Steps 2 and 7 fail: the memory is local to one machine. That is fine for one developer and not for a team.
- Step 3 or 4 fails: the server remembers, but it does not know which value is current. Agents will act on old decisions.
- Step 5 replaces the value silently: any agent can undo a person's decision. You need a rule outside the server, or a server that has one.
- Step 6 fails: do not put anything in it that part of the team should not read.

## The same test on ValorBrain

Connect both tools with the commands from [Shared memory for multi-agent teams](/en/docs/guides/shared-memory-for-multi-agent-mcp-teams). Read what the hooks send before you enable them: each prompt, up to 8,000 characters, goes to the memory engine unless you run connect with `--prompt off`.

```bash
npx -y @valorbrain/cli@latest init --agent --agent-caller claude-code --json
npx -y @valorbrain/connect@latest --token <vbm_…> --harness claude-code
```

Steps 1 and 3 are two keyed facts with the same key and different dates. The examples are illustrative, not real records.

```json
{
  "tool": "upsert_keyed_fact",
  "arguments": {
    "fact_key": "webhooks.retry.max",
    "fact_value": "3",
    "as_of": "2026-11-20",
    "evidence": "the owner changed it in the planning call; was 5 since 2026-11-10",
    "authority": "human"
  }
}
```

`authority: "human"` holds only when the token that makes the call belongs to the person who decided. Step 4 is one call from the other tool:

```json
{
  "tool": "keyed_facts_as_of",
  "arguments": { "as_of": "2026-11-15", "keys": ["webhooks.retry.max"] }
}
```

It returns the latest value for each key with a date on or before the one you asked for, so November 15 gives 5 and today gives 3. For step 5, write the same key from a token with no user behind it. The tool's contract says a weaker caller over a protected value produces a pending proposal and leaves the value in place. For step 6, store a memory with `visibility: "private"` and retrieve from a token that belongs to another user. For step 7, the export is one call:

```json
{ "tool": "export_docs", "arguments": { "format": "ndjson" } }
```

`export_docs` returns documents, up to the `limit` you pass (1,000 by default). Keyed facts are not documents: read them with `keyed_facts_as_of` for today's date and no `keys`. If any step behaves differently from what this page says, that is a defect on our side. Report it with the `feedback` tool.

Work that passes between agents is one more thing to check. None of the tool lists we read for the reference server, Mem0 MCP or Graphiti has a tool for it. On ValorBrain it is a record with a recipient and a status, covered in [Handing work from one coding agent to the next](/en/docs/guides/handoff-between-coding-agents-what-to-carry).

## What we measured on our own team

We run 13 agents on ValorBrain across sales, customer success, growth, content, finance and tech. The team usage page is rebuilt every hour and shows counts only, with no memory content. Measured 2026-11-27 at 10:07 (UTC-3):

- 13 of 13 agents used the memory in the last 7 days
- 626 keyed facts recorded since first use on 2026-07-27, of which 518 are current today
- 188 times in the last 30 days an agent declared it used a keyed fact written by another agent, across 100 different keys
- 397 times in the last 30 days an agent declared it used a document written by another agent

These are our numbers, from one team, not a benchmark, and they say nothing about any other product. They show that values written by one agent are read by another every day. They do not show that each answer was right, which is what the afternoon test is for. The live page is at [team.valorbra.in/en](https://team.valorbra.in/en/) and the raw counts at [team.valorbra.in/data.json](https://team.valorbra.in/data.json).

## Checklist

- You know where the memory is stored and you reached it from a second machine.
- You know whether access is a filter the caller passes or a permission the server checks.
- A changed value came back alone or marked current, with its date and source.
- You asked for the value on a past date and got the old one.
- You know what happens when an agent writes over a person's decision.
- You know whose model reads the conversation, if one does.
- You ran the export yourself and opened the file.
