A API hospedada em `valorbrain-api.valor.digital` é o caminho sem setup. Esta página é para rodar o engine você mesmo. Ela condensa o [`RUNNING_LOCALLY.md`](https://github.com/agentxagi/valorbrain/blob/main/RUNNING_LOCALLY.md) do repo do engine — na dúvida, aquele arquivo (e o `/openapi.json` da sua instância em execução) é a verdade.

## A stack

| Camada | O quê | Padrão |
|---|---|---|
| Runtime | **Bun** 1.x (não Node; evite o install via snap — stdin quebrado quebra hooks) | — |
| Banco de dados | **PostgreSQL 18** | `:5433`, runtime via **PgBouncer** `:6432` |
| Extensões | `vector` (pgvector), `pgturbohybrid`, `pg_ripple`, `pg_deltax` | forks proprietários no GitHub |
| Engine | REST + MCP HTTP num processo Bun | `:7438` |
| Embedding | LFM2.5-Embedding-350M (1024d) | `:7997`, ou qualquer URL de nuvem compatível com OpenAI |
| Reranker | BGE-Reranker-v2-m3 cross-encoder | `:8096`, opcional em dev (fallback in-process) |
| LLM | Gateway compatível com OpenAI | `:8201/v1`, modelo via `VALORBRAIN_LLM_MODEL` |

**GPU é opcional.** Sem uma, aponte `VALORBRAIN_EMBED_URL` / `VALORBRAIN_RERANK_URL` / `VALORBRAIN_LLM_URL` para endpoints de nuvem. Sem as extensões proprietárias do Postgres o engine ainda sobe em **modo fallback** (pgvector + BM25 via tsvector) — ok para dev, sem RRF híbrido completo nem grafo KG.

## Bancos de dados — regra número um

| Banco | Uso |
|---|---|
| `valorbrain` | **Produção.** Dados reais de tenant. Nunca rode a suite de testes contra ele. |
| `valorbrain_test` | Suite de testes (requisito duro — a suite se recusa a um banco que não se chame `*_test*`) |
| `valorbrain_staging` | Engine de staging na `:7439` |

Conexões de runtime passam pelo PgBouncer (`:6432`); migrations e DDL vão **direto para `:5433` como role `postgres`**. A role de aplicação (`valorbrain_app`) roda sob RLS e nunca faz DDL. Regra de segurança permanente: nada de `TRUNCATE`/`DROP`/`DELETE` em massa sem `WHERE tenant_id = ...` — RLS não bloqueia `TRUNCATE`.

## Setup

```bash
# 1. clone + install
git clone https://github.com/agentxagi/valorbrain ~/valorbrain && cd ~/valorbrain
bun install

# 2. databases + migrations (idempotent; as postgres, never the app role)
sudo -u postgres env PGHOST=localhost PGPORT=5433 psql -c "CREATE DATABASE valorbrain;"
sudo -u postgres env PGHOST=localhost PGPORT=5433 psql -c "CREATE DATABASE valorbrain_test;"
bash scripts/apply-engine-migrations.sh              # applies pending, registers checksums
DATABASE=valorbrain_test bash scripts/apply-engine-migrations.sh

# 3. dev tenant (prints the api_token you will use as Bearer)
bun run src/valorbrain.ts provision-tenant --slug dev --name "Dev" \
  --admin-email you@example.com --plan solo --dry-run

# 4. serve
bun run src/valorbrain.ts serve                      # REST + MCP on :7438
```

O script de migration cria `schema_migrations`, detecta números reutilizados e registra checksums — migrations aplicadas à mão passam por fora do inventário, e um inventário que mente é pior que nenhum. Migrations são **aditivas**; o runtime pula DDL no boot por design (`VALORBRAIN_SKIP_SCHEMA_BOOTSTRAP`).

Copie `.env.example` para `.env` e preencha o contrato:

| Variável | Para quê |
|---|---|
| `POSTGRES_*` / `POSTGRES_URL` | Runtime via PgBouncer `:6432`; migrations direto na `:5433` |
| `VALORBRAIN_EMBED_URL` | Endpoint de embedding (padrão `:7997`) |
| `VALORBRAIN_RERANK_URL` | Cross-encoder (padrão `:8096`); omita para o fallback in-process |
| `VALORBRAIN_LLM_URL` / `VALORBRAIN_LLM_MODEL` | Gateway e nome do modelo |
| `VALORBRAIN_API_TOKEN` | Bearer que o servidor exige (armazenado só como SHA-256) |
| `VALORBRAIN_PUBLIC_URL` | **A URL que o seu engine anuncia em `servers[]` do `/openapi.json`.** Sete antes de colocar o engine atrás de um tunnel/proxy, ou os clientes vão receber instrução de chamar `localhost` |
| `VALORBRAIN_DEV_TENANT_ID` | Tenant que suas chamadas locais de CLI sem escopo assumem |

## Serviços e portas

`systemctl list-units 'valorbrain*'` num host de produção mostra o inventário completo. As essenciais:

| Serviço | Porta | Trabalho |
|---|---|---|
| `valorbrain.service` | **7438** | Engine de produção (env via drop-ins em `/etc/systemd/system/valorbrain.service.d/`) |
| `valorbrain-staging.service` | 7439 | Engine de staging (DB `valorbrain_staging`, `/etc/valorbrain/staging.env`) |
| `valorbrain-embed-worker.service` | — | Worker contínuo de embedding |
| `valorbrain-watcher.service` | — | File watcher + pipeline de extração |
| `valorbrain-entity-worker.service` | — | Extração de entidades + enriquecimento |
| `lfm2-embed.service` | 7997 | Embeddings (CUDA) |
| `bge-reranker.service` | 8096 | Reranker (CUDA) |
| `gliner-ner.service` | 8103 | NER (CUDA) |
| `valorbrain-opencode-go-gateway.service` | 8201 | Gateway LLM |

O engine binda em `127.0.0.1` por padrão. Para expor: coloque um tunnel ou reverse proxy na frente e sete `VALORBRAIN_PUBLIC_URL` para a origem pública — o `/openapi.json` vivo reescreve `servers[]` a partir dela, e `/setup/instructions` para de mandar clientes chamarem `localhost`.

## Verifique o engine em execução

```bash
curl -sS http://localhost:7438/healthz          # liveness, no auth
curl -sS http://localhost:7438/openapi.json | jq '.servers, .info["x-valorbrain-live-operations"]'
```

A spec servida em `/openapi.json` é **gerada a partir da tabela de rotas do processo no momento do request** — `x-valorbrain-live-operations` conta o que este build de fato registrou, `x-valorbrain-missing-from-yaml` lista rotas que existem no código mas ainda não no contrato escrito, e `/openapi.yaml` serve o mesmo documento como YAML. Se o seu cliente e esta spec divergirem sobre um path, acredite na spec.

## Staging sem parar a produção

`bash scripts/staging-up.sh` sobe um engine completo na `:7439` com banco próprio e a **mesma role de engine** (`valorbrain_app`, RLS, sem BYPASSRLS) — para que benchmarking e experimentos de schema não sombreiem estatísticas ou locks de produção. `--recriar` zera o corpus, `--down` para, `--status` mostra o estado. Qualquer script que importe o store deve rodar via `scripts/bun-staging.sh` para que o `.env` da raiz (que aponta para produção) fique fora do processo.

## Gates de qualidade

Dois gates de benchmark acompanham o engine (custam tokens de LLM e tempo — não são testes de unidade):

| Gate | O que protege |
|---|---|
| `bun run gate:locomo` | Piso de recall LoCoMo nightly (R@10 ≥ 0.90 por padrão; `gate:locomo:full` para o run SOTA completo) |
| `bun run gate:beam` | Acurácia do produto no BEAM-100K via harness AMB, com par fixo de reader/judge para os números ficarem comparáveis |

O gate da suite de unidade é `bun run test` contra `valorbrain_test` — qualquer falha é regressão; não existe banda de tolerância.

## Upgrades

1. Backup primeiro: `bash scripts/backup-valorbrain.sh` (ou `pg_dump`).
2. Pull, `bun install`.
3. `bash scripts/apply-engine-migrations.sh` — só aditivas, checksum registrado.
4. Reinicie o engine; confira `journalctl -u valorbrain -p err` e `/healthz`.
5. Depois de mudanças de schema, sincronize o banco de testes antes de rodar a suite (`bun run sync:test-db`).
